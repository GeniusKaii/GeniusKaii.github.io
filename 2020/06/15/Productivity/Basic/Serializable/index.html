    Serializable 序列化

    2020-06-15 · 修改于 2026-11-24 · Basic_Definitions · AI 补完

    没有系统地学习过序列化这东西，了解一下。 Java基础学习总结——Java对象的序列化和反序列化

    以及一些经历。

    什么是序列化

    把对象转换为字节序列的过程称为对象的序列化。
    把字节序列恢复为对象的过程称为对象的反序列化。

    也就是说，把内存里的 Object 写成硬盘上的文件进行持久化保存，要用的时候再取出来。
    或者，将对象转换成字节序列（二进制）后在网络上进行传输。

    什么东西需要序列化

    判断标准只有一条：这个对象需不需要离开当前这一次 JVM 运行。

    按「离开到哪里」分三类：

    一、离开这个进程——RPC 调用。参数和返回值都要变成字节穿过网络。这也是为什么 RPC 框架里所有 DTO 必须可序列化。

    二、离开这台机器——分布式缓存、消息队列。对象要写进 Redis 或 Kafka 的字节流里，另一台机器再读出来。

    三、离开这段时间——持久化。最典型的是 Session：Tomcat 重启时会把 session 落盘，下次启动再读回来。

    三类里最容易忽略的是第三种。它不需要跨网络，也不跨机器，只跨了一次重启——但一样要求序列化。

    反过来，ThreadLocal、JDBC 的 Connection、文件句柄这些绝对不该序列化：它们代表的是「当前进程里的一个资源」，字节化之后没有任何意义。

    1. 反序列化本身是攻击面。readObject 会在还原对象时执行类里的逻辑，如果类路径上存在可利用的类，就形成反序列化漏洞链。这几年大部分 Java 远程代码执行都跟它有关。
    2. 只能 Java 读 Java。跨语言场景直接出局。
    3. 体积大、速度慢。原生格式带大量类型元信息，比 Protobuf 大好几倍。
    4. 版本兼容很脆。字段一改就可能读不出来。

    所以实际项目里通常换成：

    场景 常用方案
    对外 API / 前后端 JSON
    内部 RPC / 高性能 Protobuf、Thrift
    缓存对象 JSON 或 Kryo、FST
    配置/日志 JSON、YAML

    共同点：都是「值序列化」，只保留数据本身，不保留「这是哪个类的实例」这个信息。 这也顺带把上面第 1 条漏洞堵掉了。

    提醒

    由于序列化是根据 class 里面的 UID 来判断是否一致的，那么就存在以下两种情况：

    • 当希望 class 的版本向后兼容时，可以保持 UID 不变，那么老的（已经序列化的）文件依旧可以进行反序列化。
    • 当不希望兼容时，要更改/更新 class 中的 UID，那么进行反序列化时就会报错。

    补一句坑：只要不显式声明 serialVersionUID，编译器会按类的结构自动算一个。

    这意味着你「只是加了一个无关紧要的 private 方法」，算出来的值就可能变——然后老数据全体反序列化失败。所以规范做法是永远显式写上它，把控制权握在自己手里。

    思考

    有哪些常见类实现了序列化？为什么？

    • String

      String 实现了 Serializable（还有 CharSequence、Comparable）。这不是随手加的：

      • 它可以当 HashMap 的 key，而 HashMap 本身又要能序列化 → key 必须可序列化；
      • 它是 Session attribute 的通用载体；
      • 它是 RPC 里出现频率最高的类型。

      一句话：所有「基础到可以当积木」的类型，都必须可序列化，否则上层任何对象都串不起来。

    • Session

      这里的 Session 指 HttpSession。它需要序列化是因为两件事：

      • 重启不丢登录态：Servlet 容器在关闭时把 session 落盘，启动时读回来；
      • 集群共享：多台 web 服务器之间同步会话。

      这也解释了一个常见事故：往 session 里塞了一个没实现 Serializable 的自定义对象——单机跑得好好的，一重启或者一做集群，用户全部掉线。

    • 还有：ArrayList、HashMap、基本类型的包装类、Date、Enum、BigDecimal——都是同一逻辑：它们要能作为别的对象的组成部分被整体序列化。

    序列化之后会发生什么？

    今天碰到一个事，一个类的构造函数的一个入参是Map<String, String>，如果我传一个null进去的话，经过序列化+反序列化之后，他会变成一个空Map而不是原本的null。

    啊这？好好理解一下……

    补完：那个 null 变空 Map 的事（2026-11 补）

    先把结论放在前面：Java 原生序列化不会做这件事。

    ObjectOutputStream 遇到字段是 null 时写的是 TC_NULL 标记，读回来仍然是 null。这一点可以直接测出来：

    所以既然它变成了空 Map，说明变化发生在别的地方。按嫌疑从大到小，有四个位置：

    一、类自己在 readObject 里做了兜底

    这是最常见的原因。很多人为了让业务代码不用判空，在反序列化钩子里顺手补了个空集合。

    二、字段声明时初始化，而反序列化没有覆盖它

    原生序列化会覆盖这个初始值，但如果中间经过别的框架，或者走的是「先 new 再填字段」的路径（比如某些 Bean 映射），初始值就会留下来。

    三、序列化框架层做的转换

    这是最需要警惕的一类。原生序列化不会，但某些 RPC / JSON 框架会把 null 集合字段还原成空集合：

    • Jackson 在开启特定配置后，集合类型的 null 会写成 []，读回来就是空集合而不是 null；
    • 部分 RPC 框架（历史上 Hessian 就有过类似行为）在还原集合类型时，把缺省值当空集合处理。

    这一条我没有在你的具体环境里验证过，只是把可能性列出来。 要确认只能看当时用的是哪个框架、哪个版本。

    四、getter 里做了兜底

    字段本身还是 null，但所有调用方看到的都是空 Map。这类最容易误判——你以为数据变了，其实只是取值时被替换了。

    怎么定位

    按这个顺序查，一般三步内能锁定：

    1. 先确认字段本身是不是 null。 用反射直接读字段，别走 getter。如果字段是 null 而 getter 返回空，就是第四类。
    2. 搜这个类有没有 readObject / readResolve。 有就重点看——第一类的概率最高。
    3. 确认走的是哪个序列化器。 用 ObjectOutputStream 还是 JSON/Protobuf/Hessian？如果是后者，去查它处理 null 集合的默认行为。

    这件事真正教给我的

    「序列化」这个词很容易让人以为是一个无损搬运的过程，其实不是。

    原生 Java 序列化在语义上确实是无损的（null 还是 null，引用关系也保持），但真实系统里往往不是「纯序列化」，而是「序列化 + 框架的默认值策略 + 类的生命周期钩子」三样叠加。

    排查这类问题的关键，是先确定「哪一段才是嫌疑人」——先证明原生序列化没干，再去框架和类里找。顺序反了，就会在错误的地方翻半天。

    这也是后来我在做三方对接时反复用到的一个思路：先证伪最不该出事的那一层，剩下的范围就窄了。
